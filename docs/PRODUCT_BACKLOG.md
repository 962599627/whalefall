## 0. 阅读规则（先看这里）

### 0.1 优先级定义

| 级别 | 定义 | 对发布的影响 |
| --- | --- | --- |
| **P0** | 用户可感知的错乱/不稳定/不可用，或本版承诺能力未收口 | 不通过不发布 |
| **P1** | 明显影响体验但有可用绕行；本版应完成 | 可顺延补丁版，需 Lead 记录原因 |
| **P2** | 锦上添花，或依赖条件不具备 | 本版不排期，只登记 |

### 0.2 证据等级（验收只认证据）

| 等级 | 证据 | 说明 |
| --- | --- | --- |
| A | 构建产物 | `android/build/build-validation.json`、`aapt2 dump badging`、APK 内清单/资源 |
| B | 设备录屏/截图 | 按规范断点采集，注明设备型号/分辨率/系统版本/时间 |
| C | 代码评审 | 路径+行号级证据，由架构师/开发提供 |
| D | 离线检查 | `scripts/run_*_checks.py` 等纯 JVM 套件输出 |

**证据缺失 = 不通过**；「应该没问题」「只在我这台机器上正常」不作为通过依据。B 类证据若受本机条件限制（无 adb、无障碍受限，见 0.4），允许用户真机补证，但必须在 Release notes 标注「未在开发者环境真机验证」。

### 0.3 状态词

`待评审` / `待开发` / `开发中` / `待验收` / `已完成` / `本轮不做`

### 0.4 当前验证条件（影响验收方式）

本机为 aarch64 + proot Ubuntu，**无 adb 连接、无障碍受限**；`build-validation.json` 明确 `device_install_tested=false`、`device_playback_tested=false`。因此本轮验收以 **A 构建产物 + D 离线检查 + C 代码评审** 为主，B 类设备证据由用户/外部真机补。

## 3. Epic 与 Story

### E1 片库三端布局与稳定性（P0）

**用户场景**：用户从首页进「片库」，在手机/平板/TV 上查看观看历史、我的收藏、我的下载，删单条或清空历史。

**价值**：片库是留存核心页。现状问题（`LIBRARY_LAYOUT_SPEC.md` §0 记录）：平板横屏内容挤左、右侧大片空白；长标题把卡片撑宽、同排宽度不一致；手机端 Dock 遮挡最后一条；TV 端焦点与小按钮打架。规范已产出，本 Epic 做**收口与验收**。

**依赖与风险**：规范已冻结，风险在「实现是否已按规范合入」——需开发先确认缺口清单，未实现部分转 `待开发`。

#### E1-S1 手机片库列表行（<600dp）

- **用户价值**：单手可读、可删，最后一条不被 Dock 遮挡。
- **优先级**：P0
- **验收标准**（≤3）：
  1. 390×844 竖屏、三个页签各 ≥10 条：行高一致；标题单行省略；删除按钮可点、右缘对齐；最后一条完整露出（内容底部留白 ≥106dp）。
  2. 长标题（≥30 字）与超长来源名不撑宽行、不换行溢出；页签切换后各自滚动位置保留。
  3. 空态（0 条）显示图标+标题+说明+主按钮，页签仍可切换。
- **不做什么**：不改信息架构；不做左滑删除手势与批量多选（见 §4）。
- **状态**：待验收（实现已合入为前提，按清单复核）
- **证据要求**：B 三张截图（历史/收藏/下载）+ 一条长标题 + 空态。

#### E1-S2 平板网格（640 / 960 / ≥1080）

- **用户价值**：平板横屏不再「内容挤左、右半屏空白」，卡片整齐等高。
- **优先级**：P0
- **验收标准**（≤3）：
  1. 640×960 为 3 列、960×640 为 4 列、窗口 ≥1080 为 5 列（最多 6 列）；列间距 12/14/16；右侧全局导航栏不遮挡最右列。
  2. 同一行卡片等高；封面严格 2:3；标题固定 2 行、超长省略；不出现「一宽一窄」。
  3. 旋转或拖动窗口宽度变化后列数随宽度重排，页签与滚动位置不丢。
- **不做什么**：不做左侧分类/统计栏（`LIBRARY_LAYOUT_SPEC.md` §0.2 已否决）。
- **状态**：待验收
- **证据要求**：B 640/960/1080 三张截图 + 一条长标题；C span 计算实现位置。

#### E1-S3 TV 片库网格与遥控焦点

- **用户价值**：电视上能看清焦点、遥控可操作、不误触。
- **优先级**：P0
- **验收标准**（≤3）：
  1. 960×540 下 4 列；首焦点落在当前页签，进入网格后焦点框 3dp ACCENT + 1.02× 缩放可见且不改变布局。
  2. 遥控上下不跳空位；最后一行不足 4 张时焦点不落空位；长按 OK 删除/取消收藏需二次确认。
  3. 安全边 24/18：卡片与页签不被 overscan 裁切；卡片上不出现触屏小按钮（避免打散焦点链）。
- **不做什么**：不做 TV 卡片右上角小按钮；不做拖拽排序。
- **状态**：待验收
- **证据要求**：B 录屏（焦点移动 + 删除确认）+ 截图。

#### E1-S4 页签状态与数据操作稳定性

- **用户价值**：清空/删除不误伤、不跳顶、不丢位置。
- **优先级**：P0
- **验收标准**（≤3）：
  1. 「清空历史」只在历史页签出现，点击有二次确认；确认后列表与计数同步刷新，取消无副作用。
  2. 单条删除后列表立即刷新且不跳回顶部；连续快速删 3 条不崩、不错位。
  3. 三个页签数据互不串（删一个页签的数据不影响其他页签）；退出再进片库保持上次页签。
- **不做什么**：不做批量多选、不做云同步、不做自动清理规则改动。
- **状态**：待验收
- **证据要求**：B 录屏 20s（清空+取消+连续删）+ 截图；D 若已有离线检查则附输出。

### E2 电视台直播可用性（P0）

**用户场景**：用户打开「电视」tab 看央视/卫视（官方网页源），导入自己的频道列表、隐藏不看的台、改掉失效地址。

**价值**：直播是差异化能力，也是抱怨集中区：官方页地址会失效；播放页「轻点画面没反应」（双份 tap 判定）；chrome 用彩色玻璃压视频发脏；平板被强制转向。

**依赖与风险**：外部直播源不可控（**不承诺可播率，只承诺「可发现、可改址、可导出」**）；WebView 行为随厂商差异大，验收需注明设备。

#### E2-S1 官方直播页地址准确率与失效可修复

- **用户价值**：打开就能看；失效时不用卸载重装，自己两步换地址。
- **优先级**：P0
- **验收标准**（≤3）：
  1. 预置频道清单（央视+卫视）抽样 ≥20 个逐条实测，产出 `docs/LIVE_CHANNEL_AUDIT.md`：频道名、地址、UA、结果（可播/黑屏/需登录/地域限制）、日期。
  2. 不可播频道在列表有「失效」标记；用户可通过「改址」在 2 步内替换地址并立即重试。
  3. 改址持久化（重启保留）、可一键恢复默认；隐藏频道不出现在列表与搜索，可随时恢复。
- **不做什么**：不内置/托管/代理任何直播源；不自动抓取新地址；不保证第三方源长期可用。
- **状态**：待开发（地址审计 + 改址入口收口）
- **证据要求**：B 抽样录屏/截图 + 审计文档；C 预置清单位置。

#### E2-S2 直播播放器交互与安全区

- **用户价值**：点一下控制条就出来一次；平板不被强制转向；字幕/控制条不挡画面。
- **优先级**：P0
- **验收标准**（≤3）：
  1. 轻点画面 chrome 只切换一次（120ms 内不出现二次淡入）；垂直滑左亮度右音量，滑动期间不误切 chrome。
  2. 平板进入直播 tab/播放器不强制转向；平板竖屏播放 16:9 居中、上下黑边对称；手机进入即横屏，退出恢复竖屏且列表滚动位置不变。
  3. 顶/底栏用 `PLAYER_CHIP`/`PLAYER_SHEET` 纯黑系 token（无彩色玻璃压视频）；频道面板展开后 3s 不自动淡出；网页原生全屏时我们的 chrome 全部隐藏。
- **不做什么**：不做直播回看/录制/画中画；TV 端本版不提供搜索框。
- **状态**：待验收（交互修复合入后按 `TV_LIVE_RESPONSIVE.md` §7 逐条判定）
- **证据要求**：B 录屏（tap/滑动/面板/全屏）+ 三端截图；C 仅保留 `dispatchTouchEvent` 一处 tap 判定。

#### E2-S3 频道配置导入导出

- **用户价值**：换设备/备份时一次搬完，不用手抄几百个频道。
- **优先级**：P0
- **验收标准**（≤3）：
  1. 支持 M3U / TXT / 本项目 JSON 导入；导入前预览解析结果（共 N 个、重复 M 个、无效 K 个），确认后写入。
  2. 导出 M3U 与 JSON 两种格式，含分组、隐藏状态、自定义地址；再导入后频道集合、分组、顺序一致（去重规则：同 name+url 视为重复）。
  3. 解析失败（空文件/格式错/编码异常）给出可读错误并**保留原数据**，不出现部分写入或清空。
- **不做什么**：不做云同步/订阅自动更新、不做 EPG 节目单。
- **状态**：待开发（导入已有，导出与预览、事务性写入为缺口）
- **证据要求**：B 录屏（导入→导出→再导入）；D 解析用例；C 去重/事务实现。

### E3 首页长列表性能（P1）

**用户场景**：低端电视盒/中端手机上首页 120 张海报滚动卡顿、快速滚动白块。

**价值**：首页是首因页面。审计 P1-1：全仓 0 处 RecyclerView，首页为 `ScrollView + LinearLayout` 全量构建，24→120 张卡片全部实例化并绑定海报任务，低端设备掉帧风险高。

**依赖与风险**：与 Gradle 化解耦，可在现有 Python 构建下实施；风险是交互回归（焦点/滚动/分页），必须 C+B 双证据。

#### E3-S1 首页网格虚拟化

- **用户价值**：滚动跟手、不卡顿、不掉块。
- **优先级**：P1
- **验收标准**（≤3）：
  1. 首页/片库网格改为可复用列表（RecyclerView 或等价虚拟化）；120 条数据下首帧不创建全部卡片（评审可见：绑定数为可见区+预取，非全量 addView）。
  2. 连续快速滚动 10s 无 ANR、无白块；停止滚动后海报 1s 内补齐；不出现错位/串图。
  3. 交互不回归：点击/长按/焦点（TV）/返回恢复分类与位置与现状一致。
- **不做什么**：不迁 Compose/Kotlin；不改首页模块组成（继续观看/今日首推等）；不承诺低端机帧率数值。
- **状态**：待开发
- **证据要求**：C 代码评审 + B 录屏；有条件时附帧数据（注明设备/场景/采样）。

#### E3-S2 分页与状态保持

- **用户价值**：加载更多不闪、不重建；从详情返回还在原位。
- **优先级**：P1
- **验收标准**（≤3）：
  1. 「加载更多」只追加新卡片，已显示卡片/焦点/滚动位置不重建；加载失败显示重试且保留已有内容。
  2. 进入详情再返回：分类、已加载分页数、滚动位置/焦点恢复到离开前（误差 ≤1 行）。
  3. 500ms 内连切 5 次分类，旧请求结果不覆盖新分类内容。
- **不做什么**：不改搜索页 120 条上限；不做预加载下一页。
- **状态**：待开发
- **证据要求**：B 录屏 30s；D 调度/取消用例（若有）。

#### E3-S3 首屏性能测量基线

- **用户价值**：性能结论有数据，不靠感觉；避免把「没有实测」说成「已优化」。
- **优先级**：P1
- **验收标准**（≤3）：
  1. 产出首页冷启动/首帧基线表（设备型号、系统、版本、5 次采样 P50/P90），写明采集方法；无设备条件时明确写「未采集」，不估算。
  2. 虚拟化改造前后同设备对比（≥5 次），只给原始数据与结论，不承诺百分比。
  3. 启动 profile 口径写清：手写 `baseline-prof.txt` 已打包；未做实测 Macrobenchmark（见 §4），Release notes 不得宣称「Baseline Profile 已优化启动」。
- **不做什么**：不引入 Macrobenchmark 工具链；不升 targetSdk；不做 R8 keep 调优。
- **状态**：待开发（依赖 E3-S1 落地）
- **证据要求**：A 构建记录 + 测量表；B 采集截图/录屏。

### E4 设置内诊断与崩溃记录（P1）

**用户场景**：用户报障（卡顿/黑屏/更新失败），需要在 App 内找到版本、设备、崩溃原因并导出给支持方。

**价值**：降低支持成本、减少「凭猜测排查」。现状已有崩溃记录、运行日志、缓存清理（设置页），缺「一键导出 / 脱敏口径 / 版本信息聚合」。

**依赖与风险**：已有 `AppLog` 环形诊断与崩溃记录实现；风险是脱敏不彻底（路径/域名/账号）。

#### E4-S1 崩溃记录可读可导出

- **用户价值**：用户能自己把崩溃信息交出来，不用教人抓 logcat。
- **优先级**：P1
- **验收标准**（≤3）：
  1. 崩溃记录页展示：时间、版本名/版本号、设备型号/Android 版本、异常类型与堆栈前 N 行；空态有说明。
  2. 支持「一键复制」与「导出为文本文件」；导出内容不含账号/Token/片名/播放地址（域名、路径、query 敏感字段脱敏）。
  3. 崩溃记录有上限（最近 5 次 / 单条 ≤64KB），可手动清空；清空后不自动重建旧记录。
- **不做什么**：不做自动上报服务器、不接第三方统计、不做 ANR 全量抓取。
- **状态**：待验收（现有能力复核，导出/脱敏缺口转待开发）
- **证据要求**：B 截图（有崩溃/空态）+ C 导出样例（脱敏后）。

#### E4-S2 运行诊断页

- **用户价值**：一屏看清「我是什么版本、什么设备、什么引擎状态」，方便反馈。
- **优先级**：P1
- **验收标准**（≤3）：
  1. 一屏可见：App 版本/构建 commit、设备形态（手机/平板/TV）、系统版本、当前配置源名称与数量、扩展引擎状态、缓存占用、最近 5 条异常摘要。
  2. 支持「复制诊断摘要」，纯文本可直接粘贴；不含完整 URL、账号、片名。
  3. 无配置/离线时也能打开，不阻塞、不崩溃。
- **不做什么**：不做远程诊断通道、不做日志上传。
- **状态**：待开发（截图/复制缺口）
- **证据要求**：B 截图 + 复制文本样例；C 脱敏白名单。

#### E4-S3 缓存清理与存储可视化

- **用户价值**：知道空间去哪了，一键清干净又不误删收藏/下载。
- **优先级**：P1
- **验收标准**（≤3）：
  1. 显示各类占用：海报缓存、详情/首页快照、下载、日志、临时文件（MB），合计与系统设置中应用占用差异可解释。
  2. 单项清理与「一键清理缓存」可用；清理后数字立即刷新；正在播放/下载不受影响（明确提示不删下载/收藏/历史）。
  3. 清理失败（占用/权限）给提示不崩溃；可用空间 <200MB 时进入设置不崩。
- **不做什么**：不做自动定时清理、不做 SD 卡迁移。
- **状态**：待验收（现有能力复核，分类统计缺口转待开发）
- **证据要求**：B 录屏清理前后 + 截图；C 清理范围白名单。

### E5 更新渠道可信（P1）

**用户场景**：用户从 App 内检查更新（GitHub 多镜像），或从下载页装 APK；更新失败会一直停在旧版。

**价值**：更新链路是「用户能否拿到修复」的唯一通道。审计 P2-7/P2-8：当前发布 `git_dirty=true`（源码不可复现）、文档版本漂移（README 写 1.2.0，manifest 1.2.2）；多源回退与失败提示也需验证。

**依赖与风险**：依赖发布流程人工检查清单；本轮不做 CI 自动发版。

#### E5-S1 多镜像回退与失败可恢复

- **用户价值**：主源挂了也能更新；弱网不卡死、可续传。
- **优先级**：P1
- **验收标准**（≤3）：
  1. 主源不可用自动回退备用源（顺序固定），回退在 UI 可见（如「正在尝试备用源」），失败给可重试错误，不无限转圈。
  2. 下载中断后重试可续传；取消不残留半包；校验失败（sha256/包名/版本/签名）拒绝安装并说明原因。
  3. 弱网（飞行模式再恢复）下检查更新 30s 内给出明确结果（有更新/无更新/网络错误），不 ANR。
- **不做什么**：不做静默安装、不做自动下载全量。
- **状态**：待验收（多源已实现，按清单复核）
- **证据要求**：B 录屏（断网/恢复/重试）+ 日志；C 回退顺序与校验实现位置。

#### E5-S2 更新说明与版本一致性

- **用户价值**：下到的包、说明、版本号、源码对得上；用户信得过。
- **优先级**：P1
- **验收标准**（≤3）：
  1. 版本号单一事实源：manifest / 构建产物 / README / 更新 feed / Release notes 的版本与文件名一致；1.3.0 发布时四处交叉核对通过。
  2. 发布包 `git_dirty=false`；若无法做到，Release notes 必须标注 `-dirty` 与对应 commit（审计 P2-7）。
  3. 更新说明只写本包实际内容（不写未发布的 Flutter/iOS/插件移植），并列已知限制与「未真机验证」项。
- **不做什么**：不做 CI 自动发版；不重写历史 Release。
- **状态**：待开发（发布检查清单 + 文档收敛）
- **证据要求**：A 构建记录 + 交叉核对输出；C 检查清单。

#### E5-S3 分包渠道防串

- **用户价值**：手机不会收到电视包；装错包有明确提示。
- **优先级**：P1
- **验收标准**（≤3）：
  1. mobile 包与 TV 包分别只读自己的 feed，互不提示对方版本；相同版本号不互相覆盖（edition/包名校验）。
  2. 错误包（如 TV 包装到手机）在更新时被拒绝并提示「请安装对应设备版本」，不进入安装流程。
  3. 下载页文件名、sha256、feed 三者一致；旧客户端迁移路径写进 Release notes。
- **不做什么**：不做应用内切换版本类型；不做 Play 上架。
- **状态**：待验收（feed 已分包，按清单复核）
- **证据要求**：A 产物 + feed 内容；B 模拟错包提示。

## 6. 给 Lead 的一页纸结论：本轮建议做什么

**结论：本轮只做「2 个 P0 + 1 个 P1 主线」，其余收尾，不启动任何重架构项目。**

1. **先做（顺序）**
   1. **E1 片库三端收口**（P0，成本最低）：规范已冻结，以「验收清单 + 补缺口」为主，先把三端截图的硬伤清掉。
   2. **E2 电视台直播**（P0）：先出 `LIVE_CHANNEL_AUDIT.md`（≥20 频道抽样），再补「失效标记 + 改址」与播放器 tap/安全区修复；导入导出补预览与事务性写入。
   3. **E3 首页虚拟化**（P1，与 E2 并行）：这是本轮唯一结构性性能收益，且不依赖 Gradle；先 S3.1，S3.2/S3.3 跟随。
2. **收尾不占主开发**：E4（诊断导出/脱敏）与 E5（更新回退/版本一致性）以「验收 + 小补丁」方式完成。
3. **发布门槛（缺一不发）**
   - P0 Story 全部验收标准有证据通过；
   - E3-S1 完成且无点击/焦点/滚动交互回归（C+B 双证据）；
   - E4/E5 验收清单无 P0 缺陷；
   - 所有「未真机验证」项写入 Release notes；发布包 `git_dirty=false`（或标注 dirty + commit）。
4. **明确不做**：见 §4。特别强调——**AGP 9 全量迁移、targetSdk 升级、实测 Baseline Profile、跨端同步**本轮都不做，只出验证结论作为下版输入。
5. **风险 Top3 与对策**
   - 直播源不可控 → 不承诺可播率，只承诺「可发现失效、可改址、可导出」；
   - 虚拟化回归面广 → 必须 C 代码评审 + B 录屏双证据，禁止只凭「我这边不卡」验收；
   - 发布不可复现（dirty）→ 打包前 clean tree 写入发布检查清单。
6. **需 Lead 决策的 3 个点**
   - (a) 是否接受「无真机 adb 条件下发布，仅记录设备验证缺口 + 用户补证」？
   - (b) TV 端本版是否确认砍掉片库卡片小按钮与电视台搜索框（规范已如此定义）？
   - (c) AGP 9 验证结论是作为 1.3.0 发布前置，还是仅作为下版输入？（建议：仅作输入，不阻断 1.3.0）
7. **文档联动**：E1 → `LIBRARY_LAYOUT_SPEC.md` §9；E2 → `TV_LIVE_RESPONSIVE.md` §7；E3 → `ANDROID_AUDIT_2026.md` P1-1；E4 → 现有 `AppLog`/崩溃记录；E5 → 审计 P2-7/P2-8 与 `build-validation.json`。
